## Context

**取数链路中的 BM25 支路**（`src/rag/retrieval.py:82-96`）：

```
if HYBRID_SEARCH_ENABLED and bm25 and kb_id:
    d, b = await asyncio.gather(dense_t, bm25_t)   # ⚠ 无 return_exceptions
    results = rrf_fusion(d or [], b or [])          # b=[] 时融合结果 == dense
    log_event(Event.HYBRID_DONE, result_count=len(results))   # 照打 hybrid
```

**索引的存取**（`src/infra/search/bm25_index.py`）：

- 写入（`:36-39`）：`pickle.dump({"bm25": bm25, "chunks": chunks}, f)` —— **直写目标文件，非原子**
- 读取（`:86-117`）：`.exists()` 检查失败即 `return []`（**静默**）→ `pickle.load`（`:90`）→ 取键（`:91`）→ 打分（`:93`）→ 按下标取 chunk（`:97`）。**除 `.exists()` 外无任何异常保护**
- 调用频次：`search` 由 `retrieval.search` 每次检索调用（`retrieval.py:86`），**每次调用都全量重载索引**，无进程内缓存

**写入侧的两个并发事实**（决定了原子写与自愈必须防竞态）：

- `src/services/document_service.py:27` `asyncio.Semaphore(3)`、`:240` `asyncio.create_task(...)` —— 同一 KB 的多个文档可**并发**走到 `:572` / `:130` 的 `_rebuild_kb_index(kb_id)`，即同一 KB 的并发全量重建是真实路径。
- `src/services/document_service.py:145-150`：重建失败 catch 全部异常后**只 `logger.warning`，不落事件**，且**旧索引文件保留并继续被检索** → 该 KB 返回**过期结果**而无人知道。

**实测（2026-09-18，容器内，`b9e74e82…` 这一个有索引的 KB）**：

| 项 | 数值 |
|---|---|
| chunks / 内容字符 | 51 / 31,881 |
| pkl 体积 | 236,643 bytes |
| `pickle.load` | **58.2 ms**（冷页缓存另测为 191.9 ms） |
| `BM25Okapi` 从原文重建 | **5.6 ms** |

⚠ **实测量级仅 51 chunk**。上面"JSON 路径更快"的结论**不覆盖千 chunk 量级**；把它当普适结论是外推。

**环境约束**：`data/` 位于 `/mnt/d`，`df -T` 实测文件系统为 **9p**（原子性与锁语义弱，`fsync` 不保证与本地文件系统同等语义）；`data/` 权限实测 `drwxrwxrwx`；`data/` 被 gitignore（`.gitignore` 仅 `/data/`）。

**部署约束**：

- `docker-compose.yml:245-246` 只挂载了 `chroma_persist` 与 `ragas`，**漏 `bm25_index`**。
- `docker-compose.prod.yml:210-214` 的 app 卷只有 `app_logs` / `chroma_onnx_cache` / `./skills` / `./agents` —— **`chroma_persist` 与 `ragas` 都没挂**；该文件写 `--workers 4`，与 `CLAUDE.md`「生产单 worker」规则冲突；其 named volumes 与 `./data/*` 路径与 dev 完全相同。
- 当前运行的容器来自 `docker-compose.yml` + `docker-compose.override.yml`（`docker inspect` 的 `com.docker.compose.project.config_files` 标签），**prod compose 尚未投入使用**。

**当前状态（2026-09-18 实测）**：容器内只有 `b9e74e82…/bm25.pkl`（2026-09-16 调查时回填，236,643 bytes）；宿主机 `data/bm25_index/` 只有一个 0 字节空目录 `kb/`。`knowledge_base` 有 **1340** 行未删除，Chroma 有 **691** 个 collection、**176** 条 embedding，其中**只有 5 个 collection 含分块**。

## Goals / Non-Goals

**Goals:**

- 索引脱离容器可写层，容器重建后仍在。
- 索引文件不因写入中断而处于"截断半写"状态；即使发生，读取侧 SHALL 降级而非失败。
- 索引损坏/缺失时**降级**（纯 dense 可用），而不是**硬失败**（整条检索不可用）。
- 索引损坏后能**自愈**，不依赖人工介入，且自愈动作**不误删完好文件**。
- "混合检索名不副实"的三种形态都可见：索引**缺失**、索引**不可用**、重建失败导致索引**陈旧**。
- 消除持久化格式带来的反序列化代码执行面与跨版本脆弱性。
- 为 change `retrieval-fetch-and-dedup` 的分数采样提供"BM25 状态已固定"的前置条件。

**Non-Goals:**

- 不改检索取数与去重口径（另见 change `retrieval-fetch-and-dedup`）。
- 不做 BM25 算法调参。
- 不做索引的增量更新（每次入库重建即可；当前 KB 规模下重建成本可接受）。
- **不消除"每次检索全量重载索引"**（见 D4 的实测与 `requirements_pool.md` F-15）。
- 不引入 Prometheus 指标。
- 不修 `docker-compose.prod.yml` 的 `--workers 4` 冲突。

## Decisions

### D1：发布批次 —— 只有"格式迁移 + 挂载 + 回填"必须同一序列

**候选**：① 所有加固项必须成批落地；② 各项完全独立；③ 按"是否依赖格式迁移"分两类。

**选 ③。**

**先更正原稿的错误因果**：原稿称「只加挂载会把静默降级升级为硬失败」，此因果**不成立**。挂载（+ 宿主机目录遮蔽容器内索引）的后果是**全部 KB 变成"索引缺失"**，而缺失路径是 `return []`（`bm25_index.py:87-88`），仍是**静默降级**。硬失败需要一个**截断的索引文件**，其成因是"非原子写 + 写入被中断"，与挂载无关，且**在当前的每次文档入库重建路径上就已存在**。

**再给出真正的批次约束**：D4 选了"只读 JSON、不做 pkl 读取兼容"。而当前**唯一存在**的索引是容器可写层里的 `bm25.pkl`（宿主机没有）。因此若 F3 的代码先上线而未同时完成挂载 + 回填，新代码找不到 `bm25.json` → 该 KB 立刻降级 —— 正是本变更要消灭的状态。**这不是"安全性"要求成批，而是"格式迁移"要求成批。**

分类结果：

- **独立，可先行**：`F5` 观测（在现有 pkl 读路径上加事件，纯增量）、`F6` 清理、`F7` CLI 防护、`F9` prod 补齐、`F10` 索引陈旧可见
- **必须同属一个发布序列，中间不留观察窗**：`F3` 格式迁移 → `F4` 整段降级 → `F8` 自愈 → `F1` 挂载 → `F2` 回填
- 原因只在 F3↔F1/F2：F4/F8 与 F1 之间无依赖，它们随 F3 一起走是因为**改的是同一段读路径代码**

**编号对照**（本文用 D 编号，`proposal.md` 与 `tasks.md` 用 F 编号）：F1 挂载 · F2 回填 · F3 格式迁移 · F4 整段降级 · F5 观测 · F6 清理误建目录 · F7 CLI 防护 · F8 自愈 · F9 prod 补齐 · F10 索引陈旧可见。

### D2：加载失败一律降级为"该路返回空"，且保护范围是**整段**而非仅读取

**候选**：抛异常（让调用方感知） / 降级返回空（静默可用） / 降级 + 落事件。

**选"降级 + 落事件"。** 理由：`asyncio.gather`（`retrieval.py:87`）**没有 `return_exceptions=True`**，因此 BM25 腿抛异常会让**整个 `retrieve_kb` 失败** —— 一个可降级的支路拖垮主路。而"静默"正是这个缺陷活了半个月的原因，所以降级必须配事件。

**不修 `asyncio.gather` 的原因**：给它加 `return_exceptions=True` 会让"dense 腿失败"也变成静默 —— dense 是主路，它失败应该失败。也可以改成"`return_exceptions=True` + 对 dense 显式重抛"，但那是在共享位置做非对称判断，可读性与证明成本都更差；在支路内部收敛是更精确的边界。

**保护范围必须覆盖读文件到构造结果的整段，不能只包读取步骤。** 跨版本/结构损坏恰好落在读取之后：`data["bm25"]`（KeyError）、`bm25.get_scores()`（AttributeError）、`chunks[idx]`（IndexError）。

**降级 ≠ 删除**：降级是无条件的安全动作；删除只发生在"确定性损坏"（见 D5）。把两者混为一谈会在瞬时 I/O 故障时销毁完好文件。

**降级路径 ≠ 只读校验路径**：`search` 的加载路径在 D5 下会写盘（删除损坏文件）。任何以只读语义调用索引检查的入口（`--check`、巡检、回填前置检查）SHALL 走单独的只读校验路径（见 D6），否则"只读检查"会当场删文件。

### D3：尽力原子写 + **唯一临时文件名**

`build_index` 当前 `open("wb")` 直写目标。改为：序列化 → 写同目录临时文件 → `flush` + `os.fsync` → `os.replace(tmp, target)`。

**同目录是硬约束**：`os.replace` 要求同文件系统，跨设备会退化为"复制 + 删除"，失去原子性。

**临时文件名必须唯一**（用 `tempfile.mkstemp(dir=目标目录)`，禁用固定名如 `bm25.json.tmp`）。理由不是理论洁癖：`document_service.py:27/240/572` 使同一 KB 的并发重建成为真实路径，固定名会让两个线程互相覆盖写，`os.replace` 可能替换上另一个线程的**半写**临时文件 —— 恰好产生本变更要消灭的截断文件。唯一名 + `os.replace` 下，并发重建的结果是"后写者胜出"，两个都是完整文件。

**能力边界（必须在 spec 里写明）**：目标是 9p 文件系统，`os.replace` 与 `fsync` 在此**不保证**与本地文件系统同等语义。因此本变更承诺 **best-effort 原子性**——"把窗口缩到最小并保证遗留的是完整或不存在"，**不承诺"不可能出现截断文件"**。兜底是 D2 的读取侧降级：即使出现截断文件，检索 SHALL 降级而非失败，并留下事件。这把"不可证明的文件系统语义"换成了"可观测、可断言的行为"。

### D4：持久化格式改为**只存 chunks 的 JSON**，加载时重建 `BM25Okapi`

**候选**：① 继续 pickle 同存 `bm25` 对象与 chunks；② 只存 chunks 的 JSON，加载时重建；③ 完全不落盘，检索时按需从 Chroma 重建并进程内缓存。

**选 ②。**

理由（针对 ①）：

- **代码执行面**：pickle 反序列化可执行任意代码。索引文件所在目录权限 0777，容器以 root 运行，F1 又把它从容器可写层搬到宿主可写目录 —— 写入面扩大而防护不变。改为 JSON 后该面消失。
- **跨版本脆弱性**：① 持久化的是**类实例**，代码升级后可能反序列化失败或得到与当前版本不兼容的对象。`bm25_index.py:98-116` 的旧格式兼容分支就是这类风险的痕迹。② 只存纯文本与元数据，天然跨版本。
- **实测顺带收益**（51 chunk）：JSON 体积是 pkl 的 0.8 倍；"读 JSON + 重建 BM25"合计约 5.5 ms，比 `pickle.load` 单独一次 58.2 ms（冷页缓存 191.9 ms）快一个量级。**这不是选它的主因（安全与兼容才是），但它使这个选择不产生性能代价** —— 注意该结论**未在千 chunk 量级验证**。

未选 ③ 的理由：③ 会引入本变更不需要的耦合与风险 —— 需要跨进程的失效信号（文件 mtime 是现成的，去掉文件后要在应用层新增机制）、首次检索出现不可预测的延迟尖峰（千文档量级建索引为数秒级），且把"基础设施加固"扩成"检索数据来源重构"。③ 的价值主要在解决"每次检索全量重载"（F-15），而那应当以**加缓存**解决，不该与持久化格式捆绑决定。

**格式细节**：文件名 `bm25.json`（不复用 `bm25.pkl` —— 扩展名与内容不符会误导后来者）。内容为 `{"chunks": [{"id", "content", "metadata"}, ...]}`。**不做 pkl 读取兼容**，代价与对策见 D1：格式迁移与 F1/F2 必须同属一个发布序列。回滚同理 —— 回滚 F3 会让 F2 写出的 json 变成孤儿，因此**回滚必须与"删掉 json 后重新回填 pkl"同时进行**。

### D5：自愈删除的触发条件**收窄到确定性损坏**，并防 TOCTOU

**候选**：① 只降级 + 落事件，处置写进运维文档；② "不可用"一律删除；③ 只在**确定性损坏**时删除。

**选 ③。** ① 的后果是故障永久滞留；② 的范围太宽 —— "不可用"按 D2 包含读取失败、解析失败、打分失败、下标越界，其中**读取失败（`OSError`：瞬时 I/O、权限、文件被并发替换）与打分异常（我们自身代码缺陷）都不代表文件内容坏**，按 ② 会**销毁一个内容完好的持久化产物**，而执行删除的是一条只读检索路径（`retrieval.py:86` 每次请求都走）。

**删除的充要条件**：文件**存在**、且**内容为 JSON 解析失败或 schema 校验失败**。其余失败形态（`OSError`、打分/下标异常）只降级 + warning，不删。

**TOCTOU 防护**：读取内容 → 判定损坏 → 删除路径，这中间并发的 `_rebuild_kb_index` 可能已 `os.replace` 写入新的完好文件，随后的删除会**删掉新文件**。防护：删除前对同一路径重新 `stat`，仅当 `st_ino` 与 `st_mtime_ns`（及 `st_size`）与读取前一致时才删除。

**边界**：文件**不存在**时不执行删除；删除本身失败只记 warning、不向上抛；删除只针对索引文件，不触碰目录结构。

### D6：回填 CLI —— 加 kb 校验、禁止无参全量扫描、新增 `--check`

三件事：

- **kb 存在性校验**（`rebuild_bm25.py:49-50` 的 `kb_ids = [args.kb]` 不校验）：防**未来**误传 kb_id。**不声称**能消除宿主机 `data/bm25_index/kb/` 的成因 —— 现有代码路径对不存在的 kb 会走 `KB_CHUNKS_MISSING` 跳过、不会建目录，故那个目录另有来源（时间线早于提交 `a9a48d1`，疑为提交前手工调用 `build_index`）。
- **禁止无参全量扫描（优先级最高）**：无参形式遍历 `get_all_kb()`，而 `get_all_chunks` 内部调 `get_or_create_collection`（**不存在即创建**）。实测 1340 个 KB / 691 个 collection / 只有 5 个含分块 → 无参会新建约 **649 个空 collection** 并刷 649 条 `KB_CHUNKS_MISSING`。回填 SHALL 显式传入目标 kb 集合。
- **新增 `--check`（不写盘）**：列出"**有分块但没有可用索引**"的 KB 并落 `warning` 事件。一举解决两件事：① 它就是 F2 回填的目标集合来源（F2 的验收需要同一集合）；② 它使本次事故的真实形态（KB 有分块、索引却缺失）以 `warning` 出现 —— 单靠 `search` 侧做不到，因为 `search` 只知道 `kb_id`、无法区分"KB 本来就空"与"索引丢了"。

`--check` 需要两条**当前不存在**的只读途径，二者都必须在 task 里显式落地（否则实现者会顺手用会创建 collection 的现有途径，把噪声以另一种形式带回来）：

- **判定"有分块"**：现有 `VectorStore.list_collections()` → `ChromaClient.list_collection_names()`（`client.py:105-113`）**只返回名称**，丢掉 chromadb 返回的 Collection 对象，因此无法在"不创建"的前提下得到分块数。需新增一个只读计数访问器（直接对 `client.list_collections()` 返回的 Collection 调 `.count()`）。参照反例：`eval_ragas.py:512` 现在的写法是 `get_or_create_collection(kb_id).count()` —— 正是本变更要消灭的副作用模式。
- **判定索引"可用"**：`BM25Index` 现在只有 `search` 一条加载入口（`bm25_index.py:75-117`），而它在 D5 下同时承担自愈删除。因此必须把「带自愈的加载」与「只读校验」拆成两条路径（只读校验：读取 + 解析 + schema 校验，返回三态结果，**绝不删除**）。否则 `--check` 会在只读语义下当场删掉损坏文件，与自身"不写盘"的声明直接冲突。

### D7：重建失败导致"索引陈旧"必须可见（F10）

`document_service.py:145-150` 现状：catch 全部异常 → 只 `logger.warning` → **旧索引文件保留并继续被检索**。用户拿到的是**过期结果**，既没有降级也没有事件。

本变更新增了 JSON 序列化与原子写两条失败路径，若在 `os.replace` 之前失败，这个"可读但过期"的状态会更容易出现。因此在 `_rebuild_kb_index` 的失败分支补一条 `warning` 事件（含 `kb_id`、原因，并标明旧索引仍在服务）。这属于"让名不副实可见"的既定目标，不是范围外扩张。

### D8：`docker-compose.prod.yml` 一并补齐三处数据卷，并以"不同机"为前置

**候选**：① 只按原稿加 `bm25_index`；② 本变更不管 prod；③ prod 一并补 `chroma_persist` + `ragas` + `bm25_index`。

**选 ③。** ① 会制造不一致：索引持久化了、Chroma 还在容器可写层，prod 容器重建后出现"KB 管理页显示无文档、检索却从 BM25 返回分块"的孤儿引用。② 让 prod 继续保留静默降级。

③ 的安全性来自已核实的事实：**prod compose 尚未投入使用**（当前容器来自 `docker-compose.yml` + override），因此此刻补挂载**没有既有数据需要迁移**。

**⚠ 前置条件**：这份 prod compose 的 named volumes（如 `corporate_rag_mysql_data`）与 `./data/*` 路径与 dev **完全相同**，因此**只在不同机器上执行**。若在同一台机器上跑 prod，它会直接挂载并改写 dev 的向量与索引数据。该前置条件必须写进 compose 注释与部署文档。

**不包含**：`--workers 4` 与 `CLAUDE.md`「生产单 worker」的冲突（只补数据卷，worker 数由 prod 部署本身处理，另记于 `requirements_pool.md`）。

### D9：本变更是 change `retrieval-fetch-and-dedup` 第 5 节的前置

分数形态采样若在 BM25 半死状态下进行，会把"混合退化为纯 dense"的噪声当成信号。

- **甲**（推荐）：本变更先落地，再采样 —— 采样到的是系统的真实形态。
- 乙：先在固定并记录 BM25 状态下采样，结论里带前提标注。

**选甲**；只有当本变更被推迟时，才退到乙。

## Risks / Trade-offs

- **[挂载与容器内既有索引的关系]** → 加挂载后，容器内现有的 `b9e74e82…/bm25.pkl` 会被宿主机 `data/bm25_index/`（现仅一个空 `kb/`）**遮蔽** → 所有 KB 的 BM25 都变成"缺失"，后果是**静默降级为纯 dense**（不是检索失败，见 D1）。**顺序：F1 挂载 → 立刻 F2 回填**，中间不留观察窗。
- **[格式迁移窗口]** → 见 D1：F3 代码 + F1 挂载 + F2 回填必须同一发布序列。回滚 F3 必须同时"删 json + 重新回填 pkl"，否则 BM25 再次失效。
- **[`data/` 是 gitignore 的]** → 索引不进版本库（正确），因此"回填"是一次性的部署动作，必须在文档中写清（tasks 与 `cookbook.md` 各记一处）。
- **[9p 的原子性弱]** → 见 D3：承诺降为 best-effort，兜底是读取侧降级（可观测、可断言）。
- **[并发重建]** → 同一 KB 的并发重建是真实路径（`Semaphore(3)` + `create_task`）。唯一临时文件名（D3）保证原子性不被撤销；删除前重新 `stat`（D5）保证不误删并发写入的新文件。
- **[删除动作在只读路径上]** → 检索路径会写盘（删除损坏文件）。风险已通过"只删确定性损坏 + 重新 stat"收窄；若倾向于检索路径绝不写盘，可退回候选 ①（只降级 + 落事件 + 运维文档），代价是故障需人工恢复。
- **[陈旧索引仍可读]** → D7 只让它在日志里可见，**不消除**：旧文件仍在服务，用户仍拿到过期结果。彻底修（如失败即删旧索引，让它降级为空而不是给过期数据）是行为变更，不在本变更。
- **[一次性运维动作易被遗漏]** → F2 回填是人工步骤，若漏做则"混合检索"依然名不副实；`--check`（D6）与 F5 观测是唯一的发现手段。
- **[prod 与 dev 同机]** → 见 D8 前置条件；同机会互相污染。
- **[每次检索全量重载索引（本变更不修）]** → 51 chunk 实测 58.2 ms（冷 191.9 ms），改 JSON 后降到 5.5 ms 级但**不消除重载本身**；千 chunk 量级未实测，生产规模下会成为瓶颈。已登记 `requirements_pool.md` F-15，修法是进程内缓存 + mtime 失效。

## Migration Plan

1. **F5 观测先行**（独立）：在现有 pkl 读路径上落"缺失/不可读"事件 —— 后面每一步都能被看见。
2. **同一发布序列（不可拆，D1）**：
   1. `F3` 格式迁移（JSON + 唯一临时名 + 原子写）
   2. `F4` 整段降级
   3. `F8` 确定性损坏即删（含 TOCTOU 防护）
   4. 跑门禁：`pytest tests/ -v` + `ruff check .` + `pyright src/`
   5. `F1` 挂载（改 `docker-compose.yml`）+ `docker compose up -d --force-recreate app`
   6. `F2` 回填：紧接上一步，用 `--check` 得出的目标集合逐个 `--kb` 执行
   7. 验收：宿主机 `data/bm25_index/{kb_id}/bm25.json` 存在且对该 KB `search` 返回非空；再次 `--force-recreate` 后文件仍在
3. **F6 清理**：删宿主机 `data/bm25_index/kb/`。
4. **CLI 侧防护与检查（F7）**：`2.9` 的只读校验探针已在上面第 2 步落地（同文件、纯新增方法，不改变读路径行为，故不影响批次原子性），本步落 ① `4.2` 只读分块计数访问器 → ② `4.4` `--check` + kb 校验 + 禁止无参全量。⚠ `--check` 是上面第 2 步第 6 项（F2 回填）的目标集合来源，若第 2 步执行时它尚未就绪，用一次性脚本按 `4.2` 的只读访问器产出同一集合（**不得**改用会创建 collection 的现有途径）。
5. **F10 索引陈旧可见**：`document_service.py` 的 `_rebuild_kb_index` 失败分支落事件。
6. **F9 prod 补齐**：`docker-compose.prod.yml` 加三处数据卷 + 写"不同机"前置（D8）。

**回滚**：F5/F6/F7/F9/F10 各自独立，回滚即恢复原实现。**F3 的回滚必须与"删除 json + 重新回填 pkl 版本"同时进行**（D4）。回滚 F1 会让索引在下次容器重建时再次丢失，应同时回滚 F2 的期望。

## Open Questions

1. **缺失事件的级别与噪声**：`search` 侧缺失定 `info`（缺失是"正常但少见"，按 `logging-rules.md` 的级别语义不得用 warning），事故形态的可发现性改由 `--check` 的 `warning` 承担（D6）。缺失/不可读**每请求最多各一条**（单次检索只针对一个 bound `kb_id`），噪声来源是"大量无索引 KB 被实际检索"而非 KB 总数。是否再加"进程内该 kb_id 只记一次"的守卫，等出现真实噪声数据再定。
2. **`[retrieval]` 前缀归属**：`bm25_index.py` 属 `infra/search`，不在 `logging-rules.md` 前缀主表 `[retrieval]` 的现有归属列表（rag_tools / web_tools / retrieval.py）里。**决定**：把它补进 `[retrieval]` 归属（它就是检索层），不新建前缀。
3. **`bm25.json` 的内容契约是否要写进 spec**：spec 描述行为（加载失败即降级、不反序列化任意对象、删除只在确定性损坏时发生），格式细节（字段名）留在 design。**倾向不写进 spec**，避免 spec 与实现双维护。

# temporal-constraint Specification

## Purpose

解决相对时间表达（"这几年"、"近三年"）由 LLM 自由理解导致年份解析错误的问题。系统 SHALL 将相对时间表达解析为受约束的具体年份集合：候选年份由知识库文档元数据派生，LLM 从候选集合中选择（而非自由生成），代码层校验合法性；缺失年份由代码比对算出，作为"是否联网补充"询问的依据（用户确认后才联网）。

## ADDED Requirements

### Requirement: 候选年份集合派生

系统 SHALL 从知识库文档元数据（`meta_info` 的 year / report_period 实体）派生候选年份集合，作为时间解析的合法范围；候选集合 SHALL 为 **知识库实际覆盖年份 ∪ 最近 3 个完整年度**（排除进行中的当年）——仅从 KB 派生时，KB 只覆盖 2024 的场景下"这几年"无法解析出缺失年份（详见「缺失年份判定与询问依据」）。**季度/半年度粒度 P0 归一为年份**（2025Q1 → 2025，`derive_candidate_years` 用 `20\d{2}` 正则从 report_period 提取），精确粒度比对留 P1。**仅当会话绑定知识库时执行**（未绑定 KB 不调用检索工具，自然跳过时间解析）。

#### Scenario: 派生候选年份

- **WHEN** 检索绑定知识库的文档元数据，聚合出 year / report_period 实体（如 2023、2024、2025Q1），今日日期 2026-09-01
- **THEN** 系统生成候选年份集合 [2023, 2024, 2025]（KB 覆盖年份 ∪ 最近 3 个完整年度，季度粒度归一为年份），作为 LLM 时间解析的合法选项

### Requirement: 相对时间表达结构化解析

系统 SHALL 对含相对时间表达（"这几年"、"近三年"、"最近几年"等）的查询，调用 LLM 结合今日日期与候选集合输出结构化时间范围（JSON），LLM 只能从候选集合中选择年份，不得自由生成候选之外的年份；解析失败或含时间词但候选为空时，走"无时间约束"默认路径。

**触发条件**：解析前 SHALL 用时间词正则粗筛（`近|这|上|今|去|几|最近|前几年` 等），仅命中才调用 LLM 解析；未命中直接走"无时间约束"路径（不产生额外 LLM 调用）。**实现形态**：`parse_temporal` 为 async 函数，LLM 调用走 `get_classify_llm()`（flash 分类模型，理解+结构化输出足够，不占生产 LLM）。

#### Scenario: "这几年"解析为具体年份

- **WHEN** 用户查询"腾讯这几年业绩怎么样"，今日日期为 2026-09-01，候选年份为 [2022, 2023, 2024, 2025]
- **THEN** 时间解析层输出 `{"years": [2023, 2024, 2025], "has_temporal": true}`（完整年度，排除进行中的当年）

#### Scenario: 解析出候选范围外年份被拒绝

- **WHEN** LLM 输出年份包含候选集合之外的年份（如 2019）
- **THEN** 代码层校验拒绝该输出，回退为规则默认（最近 N 个完整年度）或走"无时间约束"路径

#### Scenario: 无时间词不触发解析

- **WHEN** 用户查询"腾讯 2024 年营收多少"（不含相对时间词，正则粗筛未命中）
- **THEN** 系统不调用 LLM 解析，直接走"无时间约束"路径，零额外调用

### Requirement: 缺失年份判定与询问依据

系统 SHALL 用代码比对"解析出的年份集合"与"知识库实际覆盖年份集合"，算出缺失年份；缺失年份 SHALL 写入 `RequestContext.missing_years` 供验证循环读取，作为**询问用户是否联网补充**的依据（而非自动调用搜索工具或注入给 LLM 自主搜索）。

#### Scenario: 知识库缺 2023/2025

- **WHEN** 解析出年份 [2023, 2024, 2025]，知识库仅覆盖 2024
- **THEN** 系统算出缺失年份 [2023, 2025]，写入 `RequestContext.missing_years = [2023, 2025]`，由验证循环据此询问用户是否联网补充

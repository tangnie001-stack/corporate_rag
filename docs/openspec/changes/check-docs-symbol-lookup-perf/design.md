## Context

`src/cli/check_docs.py` 是文档锚点防腐闸门的 CLI，在 pre-commit 里以 `doc anti-rot (all docs)`（`always_run: true` + `pass_filenames: false`）**每次提交全量运行**，扫 `docs/agents/` 下 13 篇受检文档，做锚点校验（路径 / 路由 / 符号，另有 skill 工具名锚点归 `skill-registry`）。其中符号锚点校验的判定函数是 `_symbol_exists_in_code(symbol)`。

**现状（问题）**：该函数对**每一个**符号都执行

```python
for py in _SRC_DIR.rglob("*.py"):        # 遍历在函数体内，每次调用重来
    text = py.read_text(encoding="utf-8")  # 真读盘
    for line in text.splitlines():         # 再逐行拆
        if pattern.search(line.split("#", 1)[0]):
            return True
```

即索引建在"每个符号一次"的粒度上。而 `src/` 在一轮检查内不会变 —— 第 2 次到第 N 次读到的内容与第 1 次完全一致，纯属重复。

**实测（计数方式：monkeypatch `pathlib.Path.read_text`，只统计对 `_SRC_DIR` 的调用）**：

| 指标 | 实测值 |
|---|---|
| 3 篇文档样本触发的 `read_text` | **14,367 次**（符号 297 个出现 / 191 唯一） |
| 外推 13 篇 | ≈ **62,000 次** |
| 理论最坏（每次检索都读满全树） | 574 × 174 = **99,876 次**（实测低于此上限，因命中会提前退出） |
| `src/` 下 `.py` 文件数 | **174** |
| 平均每个文件被读 | ≈ **358 次** |
| 单次符号检索：命中早 | 0.057 s |
| 单次符号检索：**未命中** | 1.954 s（必须读满 174 个文件） |
| 全量 `python -m src.cli.check_docs` | ≈ **497 s**（与观测 4–7 分钟吻合） |

**约束**：`doc anti-rot` 是 pre-commit 钩子，其耗时直接等于**每次提交的固定成本**；本仓单次提交窗口实测 2–6 分钟已构成并行会话互踩的条件（已实际发生一次提交被该钩子以 `files were modified by this hook` 中止）。

## Goals / Non-Goals

**Goals:**

- 保持**判定语义逐条不变**：仍是 `0 error / 27 warn`，每条 warn 的文档、行号、锚点、文案完全一致。
- 把符号检索的文件读取从 O(符号数 × 文件数) 降到 **O(文件数)**，并去掉逐行 Python 循环。
- 把整轮检查的**一致性**提高：一次运行基于同一份代码快照，而非跨数分钟、多次重读得到的"涂抹"视图。
- 为"闸门性能"建立可回归的规格依据（此前无 capability 覆盖文档防腐闸门本身；`skill-registry` 只覆盖其中的 skill 工具名锚点）。

**Non-Goals:**

- 不改锚点的判定口径与档位（error / warn 的划分不变）。
- 不改 `_collect_code_routes` / `_collect_known_tool_names` —— 它们本来就只扫一遍，不随符号数放大。
- 不做落盘缓存、不做跨进程共享缓存、不做守护进程。
- 不引入 `lru_cache`（理由见 D4）。
- 不动 pre-commit 配置（`always_run` / `pass_filenames` 保持不变）。

## Decisions

### D1：用「单次快照」替代「逐符号重读全树」

**选择**：新增模块级快照，把 `src/` 下所有 `.py` **剥注释后的行**拼成一个字符串，单进程只读盘一次；符号检索查这份快照。

**候选对比**：

| 候选 | 文件读取次数 | 判定成本 | 等价性风险 | 结论 |
|---|---|---|---|---|
| A. 现状（逐符号重读） | 理论上限 574 × 174 = 99,876；实测外推 ≈ **62,000** | 62,000 次读盘 + 13.7M 行扫描 | — | 被替代 |
| **B. 单次快照 + 整体正则** | **174** | 每次一次 C 层正则扫描（~0.7 MB） | 低（见 D2 论证） | ✅ **选中** |
| C. token 集合索引（切分 `[^A-Za-z0-9_]` 后查集合） | 174 | O(1) 查表 | **高**：`_` 不是 alnum，`snake_case` 会被切碎（`foo_bar` 的 token 是 `foo`/`bar`），须额外生成"按下划线分段的连续连接"才能复原语义 ⇒ 复杂度与风险都不成比例 | 不选 |
| D. 落盘缓存 / 守护进程 | 0（命中时） | 极低 | 引入失效策略（TTL/哈希/时钟），且当前**无长驻调用方** | 不选（见 D3） |

**理由**：B 的收益已接近 C（read_text 减少 357×，总耗时 ≈90×），而实现只有 2 处、判定逻辑与现状**同构**（同一个正则、同一套剥注释），无新语义。

### D2：为什么「整体正则」与「逐行正则」等价

现实现：对每行 `line.split("#", 1)[0]` 后跑 `(?<![A-Za-z0-9]){re.escape(sym)}(?![A-Za-z0-9])`。
方案：把上述剥注释后的行用 `\n` 连接成一个字符串，对**整个字符串**跑**同一个正则**。

三条理由：

1. **符号不含换行**，匹配不可能跨行 —— 拼接不会制造跨行假匹配。
2. **行首/行尾在逐行版本里是"字符串边界"，在拼接版里是 `\n`**；而 `\n` 不属于 `[A-Za-z0-9]`，两侧 lookaround 的判定结果一致。
3. **剥注释逻辑逐字保留**（含"`#` 出现在字符串字面量内也被截断"这一现状行为），故两版的输入文本逐行相同。

**实测对拍**：3 篇样本 297 个符号出现（去重 191）不一致 0 个；④ 架构评审另做独立对拍（全量 574 出现 / 285 唯一）同样 **0 不一致**，并以对抗用例逐一验过：跨行、`\r\n`、`\u2028`、`\x0c`、BOM、字符串内 `#` 截断、注释内符号、下划线相邻。

**取舍**：不采用"先 `sym in blob` 快速否定再逐行精确判定"的两段式 —— 整体正则本身已是 C 层扫描（实测全量 ≈0.94 s），两段式只增加分支与代码量，收益可忽略。

### D3：缓存形态 = 进程级模块变量，无 TTL、不落盘

**选择**：模块级 `str | None`（lazy 初始化）+ 显式失效函数。

| 项 | 决定 |
|---|---|
| 级别 | **进程级**（模块级变量；寿命 = 拥有它的那次 `python -m src.cli.check_docs`） |
| 键 | 单例；getter 校验快照来自当前根（`_SRC_DIR` 变化则重建） |
| 寿命 | 进程退出即销毁 |
| 失效 | ① 进程退出（必然发生）② 显式 `_reset_cache()` |
| TTL | **无** |
| 跨进程 / 跨会话 | **不可见**（每次提交是新进程，无共享介质） |
| 落盘 | **不做** |

**为什么不需要失效策略**：写者（人改代码）与读者（check_docs）之间**不存在一个活着的共享缓存** —— `git commit` 每次都新起进程、退出即销毁，下次提交必然重新读盘。"改了文件缓存如何更新"在进程级下不成立；只有落盘/长驻才需要 TTL/哈希/时钟那类策略。

**唯一需注意的进程内场景**：pytest 一次会话内模块只 import 一次，快照会在整个会话内存活 —— 若某用例改了 `src/` 或替换了 `_SRC_DIR` 再查符号，就会读到旧快照。现状核实：`tests/cli/test_doc_consistency.py` 目前只用 `tmp_path` 喂 `_check_skill_tool_anchors`（不碰快照），**不**替换 `_SRC_DIR`。

**防护（两道，都要）**：

- 快照 getter **校验自己来自哪个根**（`_SRC_DIR` 变化即重建）—— 防御性，成本可忽略；
- 在 `tests/cli/` 加 **autouse fixture**，每个用例后调显式失效函数 —— 使新增的边界用例（临时 `_SRC_DIR` + 注释内符号）不会污染同会话的其他用例。

### D4：不加 `lru_cache`

**选择**：本次**不**引入 `lru_cache`。

**理由**：去重 574 → 285 只省约 0.5 s（相对改后 ≈5.5 s 是小头），而代价是引入**第二个失效点** —— memo 挂在**函数对象**上、快照挂在**模块变量**上，显式失效若只清一个就会**静默返回旧结果**（最难查的一类 bug）。

**若将来确需**（如符号数涨到数千）：正确形态是把 memo **放进同一份快照对象**（如 `@dataclass _SrcIndex{root, blob, memo}`），使"清快照"与"清 memo"是同一个动作，不可能失配。本次不预先引入该结构。

### D5：接受"提高一致性"这一副作用为正向收益

改后整轮检查基于**同一份快照**。现状每次检索都重读，而这些重读横跨约 8 分钟 —— 期间若工作区被改动，不同符号可能看到文件的不同版本，**同一轮结果不确定**。故本变更不是"用一致性换性能"，而是两边同时改善。

### D6：有意保留两处现状边界行为（不修，仅登记）

**决定**：本次**不修** (a) `#` 截断与 (b) `UnicodeDecodeError` 不捕获，改为在 `requirements_pool.md` / `defensive-patterns.md` 登记。

**理由**：本次唯一的强证明是"改前 / 改后全量输出 0 差异"。任何行为改动都会把这层证明从"整体等价"退化为"逐例论证"，代价与收益不成比例。

两处的严重度**不对称**，必须分开记 —— 这是本决策的关键：

| | (a) `#` 截断 | (b) `UnicodeDecodeError` 不捕获 |
|---|---|---|
| 机制 | `line.split("#", 1)[0]` 把**字符串字面量里的 `#`** 也当注释起点，该行后半被丢弃 | 现状只 `except OSError`，而 `UnicodeDecodeError` 是 `ValueError` 子类 → 直接抛出 |
| 失败方向 | 只能 `True → False`：把**真实存在的符号误报为"未检索到"** | 整个 CLI 崩 → **该次提交被拦** |
| 后果 | 多一条 `warn` 噪声（不影响退出码、不拦提交） | **单个非 UTF-8 的 `.py` 可挡死全员所有提交**（该钩子 `always_run`、无 `files` 过滤） |
| 今天可达吗 | 可达 | **不可达**（本仓无非 UTF-8 文件） |
| 登记去向 | `requirements_pool.md` | `defensive-patterns.md`（缺陷类别）**并** `requirements_pool.md`（待修项，约 1 行 `except`） |

**(b) 为什么明知是"单点故障"也不顺手修**：它今天不可达，修它**买到的是零**，却要削弱本次唯一的强证明；而登记是零成本。且正因为"不可达 → 永不被自然触发提醒"，**不登记就等于永久遗忘** —— 将来某天"全员提交突然被挡"将无从对照。

## Risks / Trade-offs

- **等价性风险** → 已用"逐条对拍（三篇样本 297 符号 0 不一致）+ 三条等价性论证 + ④ 评审的独立全量对拍与对抗用例"压制；实施后仍按 tasks 做**改前/改后全量输出逐条 diff**（error + warn 的行号与内容），不一致即回滚。
- **异常语义必须复刻** → 现状逐文件 `try: read_text except OSError: continue`（**跳过**不可读文件）。快照 getter 若不复刻，任一不可读或竞态删除的 `.py` 会让每次提交的闸门从"跳过"变成**硬失败**（该钩子无 `files` 过滤，每提交必跑）。`tasks.md` 2.1 已明确要求复刻该 `try/except OSError: continue`；`UnicodeDecodeError` 按现状**不**捕获，并在 docstring 写明。
- **唯一的理论差异面是跨行边界** → 除非符号含换行，否则不存在；已由对抗用例覆盖，tasks 中另加一条"两行拼接"的边界验证。
- **注释剥离的现状行为被固化**（`#` 在字符串字面量内也被截断）→ 这是**保持现状**而非新引入；如需修正应另开变更，不在本次范围。
- **内存占用** → 快照约 0.7 MB，一次性，可忽略。
- **`.py` 数量增长** → 快照成本随之线性增长（读 174 个文件 ≈1.4 s），但符号检索不再放大它；只要"文件数"而非"文件数×符号数"增长，即符合规格意图。
- **回滚** → 单文件、2 处改动、无迁移、无外部状态；`git revert` 即可。无破坏性操作。
- **对并行会话的意义** → 提交窗口由 4–7 分钟缩到秒级，直接降低本仓已发生过的"长窗口内并发写入 → 钩子报 `files were modified by this hook`"概率。

## Migration Plan

不适用（无部署、无数据迁移、无配置变更）。发布即随 pre-commit 钩子在下次提交时生效；回滚 `git revert`。

## Open Questions

（经 ④ 架构评审，本节两问已定，无遗留阻塞项。）

1. **性能阈值** → 采纳评审建议**保留 60 秒**：比改造后基线（约 5.5 s）留约 10× 余量，比回归态（约 497 s）低约 8×；测量环境已写入规格，避免未来在冷 NFS 等环境误判。
2. **守卫方式** → 采纳评审建议：**加确定性"读取次数"断言**（替换 `pathlib.Path.read_text` 计数，断言读取次数不随调用次数增长），**不加耗时断言**（避免把机器性能引入测试导致 flaky）。这修正了本节原先只考虑耗时断言、因而倾向"不加守卫"的偏差 —— 那会让最核心的 requirement 失去回归保护。

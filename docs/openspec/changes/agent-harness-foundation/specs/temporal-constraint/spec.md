# temporal-constraint Specification

## Purpose

解决相对时间表达（"这几年"、"近三年"）由 LLM 自由理解导致年份解析错误的问题。系统 SHALL 将相对时间表达解析为受约束的具体年份集合：候选年份由知识库文档元数据派生，LLM 从候选集合中选择（而非自由生成），代码层校验合法性；缺失年份由代码比对算出并注入检索/搜索。

## ADDED Requirements

### Requirement: 候选年份集合派生

系统 SHALL 从知识库文档元数据（`meta_info` 的 year / report_period 实体）派生候选年份集合，作为时间解析的合法范围；候选集合 SHALL 与知识库实际覆盖的报告期粒度一致（KB 有季度/半年度粒度时一并纳入）。

#### Scenario: 派生候选年份

- **WHEN** 检索知识库文档元数据，聚合出 year / report_period 实体（如 2023、2024、2025Q1）
- **THEN** 系统生成候选年份集合 [2023, 2024, 2025]（含季度粒度），作为 LLM 时间解析的合法选项

### Requirement: 相对时间表达结构化解析

系统 SHALL 对含相对时间表达（"这几年"、"近三年"、"最近几年"等）的查询，调用 LLM 结合今日日期与候选集合输出结构化时间范围（JSON），LLM 只能从候选集合中选择年份，不得自由生成候选之外的年份；解析失败或含时间词但候选为空时，走"无时间约束"默认路径。

#### Scenario: "这几年"解析为具体年份

- **WHEN** 用户查询"腾讯这几年业绩怎么样"，今日日期为 2026-09-01，候选年份为 [2022, 2023, 2024, 2025]
- **THEN** 时间解析层输出 `{"years": [2023, 2024, 2025], "has_temporal": true}`（完整年度，排除进行中的当年）

#### Scenario: 解析出候选范围外年份被拒绝

- **WHEN** LLM 输出年份包含候选集合之外的年份（如 2019）
- **THEN** 代码层校验拒绝该输出，回退为规则默认（最近 N 个完整年度）或走"无时间约束"路径

### Requirement: 缺失年份判定与注入

系统 SHALL 用代码比对"解析出的年份集合"与"知识库实际覆盖年份集合"，算出缺失年份；缺失年份 SHALL 作为 `retrieve_kb` 工具结果的附加信息注入给 LLM（明确告知缺失年份并指示对缺失项调用 search_web 补充），而非自动调用搜索工具；`RequestContext` SHALL 记录缺失年份供验证循环读取做完整性验收。

#### Scenario: 知识库缺 2023/2025

- **WHEN** 解析出年份 [2023, 2024, 2025]，知识库仅覆盖 2024
- **THEN** 系统算出缺失年份 [2023, 2025]，在 `retrieve_kb` 返回文本中追加"知识库仅覆盖 2024 年，缺失 2023/2025，请对缺失年份调用 search_web"，且 `RequestContext.missing_years = [2023, 2025]`

# ADR-0002：prompt 载体迁到 Git 内 YAML，终态为远端读取

- **Status**：Accepted
- **Date**：2026-09-18
- **Deciders**：用户（决策）；Claude（调研与实测）

## 背景与问题

**现状**：19 个 prompt 常量以 Python 字符串字面量写在 `src/config/prompts.py`（322 行）。产品侧无法编辑，任何文案调整都要改 `.py`、走代码评审与发版。

**触发事件**：本轮的改动中，只需调整一处措辞（检索阶梯的归属与出口）就必须修改 `.py` 文件 —— 载体与内容混在一起，是每改一次都要付的成本。

**仓库内既有立场（正面冲突）**：`docs/agents/requirements_pool.md:143-146` 明确主张"运行时管理优于 Git 管理"、"Langfuse 作为唯一权威来源"、"避免双轨制"，并称"给产品开 Git 权限是安全红线"。本条与 YAML 方案需要正面回应这个立场，不能静默绕过。

**同域生产参照**：WeKnora 用 `config/prompt_templates/*.yaml`（11 个文件）管理模板，结构含 `id` / `name` / `description` / `mode` / `default` / `i18n`（4 语言）/ `content`。

**既有否决**：`docs/tmp/deep-research-prompt-management.md` 第四部分已否决引入 Jinja2（依据是 dify 双语法并存的教训），占位符只做"仅标识符式替换、未知变量原样保留"。

## 候选方案

| 方案 | 做法 | 代价 | 收益 |
|---|---|---|---|
| A | 保留 Python 常量 | 产品无法编辑；文案改动走代码评审与发版 | 零迁移 |
| B | 外置为 Markdown 文件 | md 无结构化字段（id / mode / 段名），只能靠文件名与前置约定 | 可读性好 |
| C | **Git 内 YAML，加载入口与数据源解耦** | 引入一个加载器与文件契约；prompt 从编译期常量变为运行期读取 | 有结构化字段；与 WeKnora 同形态；可平滑迁到远端 |
| D | 直接上 Langfuse / DB | 现在没有产品角色与远端服务；prompt 变运行时数据 → 编译期无检查、code review 看不到、测试难覆盖 | 一步到位 |

## 决策

**选 C，并明确分两阶段：**

```
第一阶段（本期）  Git 内 YAML，开发维护
        ↓  只换数据源实现，不动段模型
终态              远端数据读取，产品维护
```

加载入口 SHALL 设计成可替换的数据源，使第二阶段是"换实现"而非"改结构"。本期 SHALL NOT 实现远端数据源。占位符只做仅标识符式替换（`{identifier}`），未知变量原样保留。

## 理由

**最关键的一行：本期要解决的是"prompt 与代码混杂"，不是"管理权归属"。**

- **A 解决不了前者**；**D 现在没有使用方**（没有产品角色、没有远端服务）。用 D 的代价（prompt 变运行时数据）去换一个当期不存在的收益，是拿确定性风险买未来的便利。
- **C 是 B 的超集**：YAML 提供了 B 缺的结构化字段（`id` / `mode` / 段名），而结构是分段模型（ADR-0003）的前提。
- **与 `requirements_pool:143-146` 是同方向的两阶段，不是对立**：终态与该处主张一致（远端读取、产品维护、Git 不作权威源）。因此本 ADR 不构成对那条立场的推翻，只是把它的实施顺序写清楚 —— 这也是本 ADR 必须存在的原因（否则后人会把两阶段读成路线反复）。
- **载体形态已有生产验证**：WeKnora 在同一形态上运行，不是设计推演。
- **不引入模板引擎**：沿用既有否决。只做标识符替换，未知变量原样保留 —— 这样"模板里写了什么"与"最终 prompt 长什么样"保持可追溯。

## 后果

**正面**：

- 文案改动不再需要改动 `.py`，产品参与的成本从"改代码"降为"改数据文件"。
- 模板获得结构（`id` / `mode` / 段名），成为分段模型与条件注入的落点。
- 加载入口与数据源解耦，为"产品维护"的终态预留了实现位。

**负面 / 接受的代价**：

- prompt 从**编译期常量**变成**运行期读取的文件**：需要处理文件缺失、YAML 解析失败、模板 id 冲突等路径，这些在常量方案里不存在。
- 所有 prompt 消费方都要经过加载器：`src/rag/prompt.py`、`src/infra/llm/prompt_manager.py` 的兜底拼接、`src/cli/compare_rewrite.py` 等 CLI、以及 fork 子代理。
- 测试面扩大：需要覆盖加载失败的降级行为，而不只是内容断言。
- 是**前置闸门约束**：载体迁移阶段（P0）要求最终 prompt **逐字不变**，该阶段不允许同时改内容或结构，否则无法证明搬运无损。

**不解决的问题**（避免后人误以为本 ADR 管了它）：

- 不做 i18n（WeKnora 模板含 4 语言块；本项目为中文单语，只保留结构位置）。
- 不实现远端 prompt 服务与产品侧编辑器。
- **不解决"规则住哪一层"的问题** —— 那是与之独立的另一条决策，见 ADR-0003。载体与分层可分别变更：可以 6 段住在 Python 常量里，也可以 YAML 装平铺的 19 个键。
- 不改任何 prompt 的内容（P0 阶段明确要求零行为差异）。

## 复查触发条件

- **出现"产品需要独立改文案且不能走发版"的实际需求** → 启动第二阶段（远端数据源）。这是本决策的主要预设兑现点。
- 若加载失败的处理无法覆盖实际故障形态（如多实例间文件不一致、热更新需求）→ 重新评估是否跳过文件阶段直接上远端。
- 若 `requirements_pool:143-146` 的立场被正式采纳为"必须立刻上 Langfuse" → 本 ADR 的第二阶段需提前，但第一阶段（结构与契约）仍不必推翻。
- 若模板文件数量增长到需要更细的目录分层（如按领域分目录）→ 复查目录约定，但这不改变"Git 内 YAML"这一决策本身。

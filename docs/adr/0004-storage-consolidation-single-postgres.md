# ADR-0004：三套存储收敛到单个 PostgreSQL 实例（含共享实例的运维后果）

- **Status**：Accepted
- **Date**：2026-09-20
- **Deciders**：用户（决策）；Claude（调研与实测）

## 背景与问题

**现状**：系统把数据分散在三套彼此独立的存储里，各自可有独立的故障状态。

| 数据 | 载体 |
|---|---|
| 关系型（7 张表） | MySQL 8.0 + SQLAlchemy 2.0 async（`mysql+aiomysql`） |
| 分块与向量 | ChromaDB 嵌入式 `PersistentClient`，**每知识库一个 collection** |
| 词法索引 | 进程内 `rank_bm25.BM25Okapi` + pickle 索引文件 |

**根本病根：三套存储 = 三个独立故障域，失败不原子。** 三者可各自半死 —— 词法索引挂掉而关系型完好，系统会一边静默降级、一边照打「混合检索完成」。

**触发事件**：`trace_c54ce259` 的缺陷活了半个月无人发现（一手记录见 `docs/tmp/deep-research-trace-c54ce259.md`）。它暴露的不是"某个支路缺观测"，而是"半活状态可以被伪装成正常"。

**实测环境事实**（完整记录见 `docs/tmp/postgres-probe-2026-09-19.md`）：Chroma 里有 **691 个 collection、176 条向量，其中只有 5 个 collection 含分块** —— collection-per-KB 的粒度制造了大量空 collection，也说明"派生存储与源数据不同库"会让不一致长期沉积。

**生产形态约束**：生产的 MySQL / Redis 已是阿里云托管高可用，真正的单点只剩向量库与文件存储；而 Chroma 没有托管形态。因此"收敛到 PostgreSQL"同时是托管化的前置路径。

## 候选方案

| 方案 | 做法 | 代价 | 收益 |
|---|---|---|---|
| ① | 三套各自加固（给词法索引补持久化、原子写、损坏自愈、降级观测） | 保留三个故障域，"半活"状态依旧可伪装；加固本身有长期维护成本 | 不动现有架构 |
| ② | **一个 PostgreSQL 实例、两个 database（应用 + Langfuse）** | 故障域共享（见「负面 / 接受的代价」四条） | 失败模式原子化；与生产 RDS 形态对齐；独立 database 给 Langfuse 独立的 DDL 空间 |
| ③ | 一个实例、同库不同 schema | Langfuse 的 `prisma migrate deploy` 与应用的迁移在同一库内共享 DDL 空间，迁移权限更难隔离 | 少建一个 database |
| ④ | 两个独立实例 | 多一个实例的成本与运维；仍需各自处理扩展、账号、备份 | 故障域完全隔离 |

## 决策

**选 ②。**

一个 PostgreSQL 实例承载应用库与 Langfuse 库；关系型表、`chunks`（pgvector 向量 + `tsvector` 生成列）全部落在这一个实例内。词法检索不再有独立的索引文件。

## 理由

**最关键的一行：三套存储的病根不是"某一套不够健壮"，而是"三个故障域允许半活状态伪装成正常"；把载体合并进一个事务域，这一类缺陷就结构性消失，而不是被观测和自愈掩盖。**

- **与生产托管形态对齐**：生产就是一个 RDS 实例。本地形态与生产形态同构，托管化时只需换连接地址，不改装配。
- **成本与运维最省**：只维护一个存储实例（一套备份、一套升级、一套账号）。
- **独立 database 而非同 schema**：Langfuse 需要迁移权限，官方支持用 `DIRECT_URL` 单独给迁移账号；给它独立的 database 才能划出独立的 DDL 空间，不与应用迁移互相干扰。
- **否决 ①**：给词法索引加持久化 / 原子写 / 自愈 / 降级观测正是 `bm25-index-durability` 的 38 个任务方向 —— 补的是症状，靶子（索引文件）本身在新形态下不存在。
- **否决 ③/④**：③ 牺牲了 Langfuse 迁移权限的隔离；④ 用"多一个实例"换来的隔离，代价高于本阶段需要。

## 后果

**正面**：

- **失败模式原子化**：存储整体可用或整体不可用，不再存在"某一支路半死而整体表现正常"的状态可供伪装。
- 分块写入与文档状态可在同一事务内提交，孤儿类缺陷结构性消失。
- 空 collection 这一类缺陷结构性消失（`kb_id` 列 + 外键取代 collection-per-KB）。
- 词法索引文件的持久化、原子写、损坏自愈、缺失降级观测 —— 这些问题的载体一并消失。

**负面 / 接受的代价**（共享实例的运维后果，四条显式接受，来源 `design.md` D1）：

1. **备份与 PITR 是实例级的**：恢复应用库会同时回退 Langfuse 的数据，两个应用的恢复点被绑死。
2. **连接数是共享预算**：prod 实为 `--workers 4`，叠加 `pool_size=10 + max_overflow=10` ≈ **80 连接**，再加 Langfuse 与其 worker，可能触及实例的 `max_connections`。连接预算必须作为 RDS 规格的输入。
3. **大版本升级是实例级维护窗口**：两个应用必须同时兼容新版本。
4. **账号模型**：现有 compose 只创建了一个用户；"独立 database + 独立账号"需要额外的创建步骤与权限划分。

（缓解：Langfuse 属于低写入负载（只存元数据，trace 在 ClickHouse），且用独立 database 隔离。）

**不解决的问题**（避免后人误以为本 ADR 管了它）：

- **本阶段只做本地**：远程 RDS 与 prod 安装是遗留项（需求池 **F-16** RDS 托管化切换、**F-17** prod `--workers 4` 与连接预算），本 ADR 不承诺完成它们。
- 只读副本 / 跨实例容灾**不在范围内**。
- 不做 Langfuse 服务端版本选择（v2 与"仅 PG"的决议另案）。

## 复查触发条件

- **需要独立备份窗口或独立升级窗口时** —— 这是"共享实例"预设被打破的第一个信号，应重新评估 ③/④。
- **连接预算逼近实例上限时** —— 届时须处置 prod 的 worker 数与连接池（F-17）。
- **迁到 RDS 时**：把上面第 2、4 条作为实例规格与账号规划的输入。

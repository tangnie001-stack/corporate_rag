# ADR-0006：中文词法检索 = jieba 预分词 + tsvector('simple') + 前缀 OR

- **Status**：Accepted
- **Date**：2026-09-20
- **Deciders**：用户（决策）；Claude（调研与实测）

## 背景与问题

**触发问题**：词法索引从进程内的 `rank_bm25` + pickle 文件迁到 PostgreSQL 全文检索后，中文必须真正可检索。两个已实测的事实决定了不能直接用默认能力：

- **PG 默认分词器不对中文分词**：实测 `to_tsvector('simple','营业收入同比增长率保持稳定')` 只产出 **1 个 token**（整串 CJK 不作切分），因此 `plainto_tsquery` 的词项永远匹配不上（实测记录见 `docs/tmp/postgres-probe-2026-09-19.md`）。
- **旧的字符级 unigram 会把词拆碎**：`rank_bm25` 的字符级索引把「资产负债率」拆成 6 个单字，任何含「资」或「产」的 chunk 都被命中，精确词项反被淹没。

**约束**：栈上不能假设云厂商预装了中文分词扩展。本地实测 `pgvector/pgvector:pg15` 的 `pg_available_extensions` 只有 `vector` (0.8.6) 与 `pg_trgm` (1.6)，**无法在本地验证任何中文分词扩展**。

## 候选方案

| 方案 | 做法 | 代价 | 收益 |
|---|---|---|---|
| ① | 引入 PG 中文分词扩展（`zhparser` / `pg_jieba`） | 扩展需云厂商预装并进 `shared_preload_libraries`，**可用性未确认**；本地无法验证 | 真分词，最接近"中文 BM25" |
| ② | `pg_trgm` 三元组相似度 | 语义是 `similarity()` 三元组相似度，**不是词项加权** | 官方镜像自带，本地已实测可用 |
| ③ | ParadeDB `pg_search` | **无托管形态**，破"能用托管就用托管"原则 | 库内真 BM25（tantivy） |
| ④ | **Python 侧 jieba 预分词 + `to_tsvector('simple')`** | 写入与查询两侧必须同源，且 `content_seg` 落库即固化（见「三个硬约束」） | `simple` 配置在任何 PG 上都可用，不依赖任何 PG 扩展 |

## 决策

**选 ④。** 写入侧用 jieba 预分词生成 `content_seg`，`tsv` 是它的 `to_tsvector('simple', content_seg)` 生成列；查询侧用同一份分词口径构造前缀通配查询串。

## 理由

**最关键的一行：`simple` 配置在任何 PostgreSQL 上都可用，而所有扩展方案都要求 RDS 预装并进 `shared_preload_libraries`（可用性未确认）；把分词放到 Python 侧，就把这份不确定性换成了一个已声明的依赖。**

- **不依赖 PG 扩展**：`simple` 是内置配置，托管 PG 必然可用；扩展方案在 RDS 上的可用性本变更无法确认。
- **`pg_trgm` 语义不对**：它给的是三元组相似度，不是词项加权，与"词项命中"不是同一个量。
- **`pg_search` 无托管**：破"能用托管就用托管"原则。
- **依赖已在仓库**：`jieba` 已声明在 `pyproject.toml` 却全仓零调用（僵尸依赖），本变更让它接线。

**连接符的选择与依据 —— 取前缀 OR，依据分两层：**

- **暴露的实测事实**（服务路径 E2E）：前缀 AND 下，自然语言查询被改写为「资产负债率 变化 趋势」时，语料不含 `变化`/`趋势` ⇒ AND 谓词为空 ⇒ `sparse_count=0`，**词法路对典型多词自然查询贡献为零**（"混合检索"退化为纯 dense）。翻转后同一类查询 `sparse_count=1`。对照与日志见 `docs/tmp/p3-acceptance-2026-09-19.md`（AND 臂 `trace_c7182b58…` `sparse_count=0`；OR 臂 `trace_791db44b…` `sparse_count=1`）。
- **探针的 `prefix-OR` 比 `prefix-AND` 高的 10.0pp 不构成质量证据**：18/30 vs 15/30 是**超集谓词的机械后果** —— 判据是集合成员、候选集 ≤ k=30，OR 是 AND 的超集，命中数必然不低于 AND。数字与口径见 `docs/tmp/p3-lexical-probe-2026-09-19.md`。
- **精度交由下游承担**：本层取召回取向，精度由 RRF / 去重 / rerank 负责，不靠收紧谓词。

**并且写明探针的边界**：探针的判据是**集合成员**（"含该词项的 chunk 是否进 top-k"），且过滤臂候选集 ≤ k，**结构上测不了排序质量**（C 组 `ts_rank`/`ts_rank_cd` 的零差是必然，不是"两函数同分"）。因此**词法路的端到端质量评估仍在语料到位后**，登记为需求池 **F-30**；在此之前不得把探针数字当质量基线。

**三个硬约束**（三者都是"不报错、只静默降召回"的入口，每一处都必须有守卫测试）：

1. **写入与查询必须同一分词入口** —— `src/infra/search/tokenizer.py`；`content_seg` 落库即固化（`tsv` 是其生成列）。因此 jieba 版本或词典一旦变更，存量 `content_seg` 与新的查询侧就不再一致 → **必须跑 `scripts/rewrite_content_seg.py --apply`**（其 `--check` 非零退出即表示存量已过期）。"同一进程内两函数比较"的守卫测试**抓不到**这种版本漂移。
2. **查询串必须在应用层构造** —— `src/infra/db/lexical_query.py`：先按安全字符集剔除（`\W`），再输出 `词元:*`（前缀通配），以 ` | ` 连接；词元全被滤空时回退为**原文子串匹配**（`content LIKE '%…%'`）。**用户原文不得直接交给 `to_tsquery`**：含空格会抛 `ERROR: syntax error in tsquery`，`a:` 会被静默吞字符得到 `'a'`。
3. **字段名不叫 `bm25_score`** —— `ts_rank` / `ts_rank_cd` 是 cover-density 排名，**不是 BM25**；本栈用 `lexical_score`，以免重复 `financial_rag-main` 的误导命名。

（单字过滤规则集中在 `src/config/const.py` 的 `LEXICAL_MIN_TOKEN_LEN = 2`：中文高频虚词本身就是单字，纳入检索文本会淹没精确词项的排序；长度过滤同时干掉空格与中文标点，无需另维护停用词表。）

## 后果

**正面**：

- 中文词法检索真正可用，且**不依赖任何 PG 扩展** —— 托管化时不需要 RDS 预装。
- 词法索引不再有独立文件，随存储收敛一并消掉其持久化与生命周期问题。
- 写入侧与查询侧共用一份分词口径，口径漂移有可执行的检查（`--check`）与修复（`--apply`）。

**负面 / 接受的代价**：

- 写入与查询两侧**必须同源**；分词器 / 词典 / 版本变更都必须触发 `content_seg` 全量重写 —— 遗漏不会报错，只会静默降召回。
- 查询串的构造与转义是抛错面（`to_tsquery` 对含空格/操作符的输入会抛异常），须由固定的构造入口承担，不得绕过。
- 前缀通配会带来误召回（如 `增长:*` 命中 `增长率`/`增长量`），且无法命中词元中间的差异 —— 精度依赖下游收口。

**不解决的问题**（避免后人误以为本 ADR 管了它）：

- **`ts_rank` 不是 BM25**：真 BM25 需 ParadeDB 或应用层自算，属另案。
- **HNSW 与中文分词的进一步调优不在本变更**。
- **176 分块语料上无法给出质量结论** —— 探针只用于同一语料上的横向配置比较（相对判据），不是发布判据。

## 复查触发条件

- **语料到达量产（千文档级）后**：重做词项命中与端到端评估 —— 这是 F-30 的兑现点。
- **RDS 侧确认可预装 `zhparser` / `pg_jieba` 时**：对比扩展方案与 jieba 预分词的选型。
- **排名质量成为可观测问题时**：当前 `ts_rank` 只是兜底排序，届时重估打分函数甚至真 BM25。

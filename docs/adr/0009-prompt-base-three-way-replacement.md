# ADR-0009：`base` 段按三选一（替换）解析

- **Status**：Accepted
- **Date**：2026-09-21
- **Deciders**：用户（决策）；Claude（调研 + 独立评审后的修正）
- **Supersedes**：ADR-0003 的**决策 3**（局部；ADR-0003 其余决策继续有效，其 `Status` 保持 `Accepted`，正文不作改动）

## 背景与问题

**决策内容本身不变，改变的是它的记录方式与理由的完整度。**

ADR-0003 于 2026-09-18 在**同一天内原地修订**了它的决策 3：原为"`base` = 领域默认 base **+** 预设 overlay（叠加）"，改为"**三选一（替换）**"。它在头部写明了当场不新开 ADR 的理由（修订发生在实施之前；为半条子决策新开取代 ADR 会连带作废仍有效的主决策）。

一次独立架构评审（2026-09-21）指出该做法在 `docs/adr/` 内造成**两套先例**：同目录的 ADR-0008 面对"要推翻 0007 的一条子决策"时，选择的是**追加新 ADR 并明写"不能改写 0007 那一行"**。两套做法并存会让后续读者无法判断哪条决策在哪个时点成立。

同一次评审还发现 ADR-0003 该处有两处事实引用错误、一处归属错误（见「对本 ADR 前置记录的更正」）。按"不可变"原则不改 ADR-0003 原文，改在此登记。

## 候选方案

| 方案 | 做法 | 代价 | 收益 |
|---|---|---|---|
| A | 保持现状（ADR-0003 的原地修订留痕） | 与 ADR-0008 的先例冲突；引用错误无处更正 | 零成本 |
| B | 改写 ADR-0003 正文（恢复"叠加"、删除修订记录） | 抹掉已生效的决策；违反"只追加" | —— |
| C | **追加本 ADR，正式化"三选一（替换）"，并登记更正** | 与 ADR-0003 形成半条取代关系，读者需同时看两份 | 与 ADR-0008 先例一致；错误有处可查 |

## 决策

**选 C。`base` 段按三选一（替换）解析，且不提供追加 / 合并开关：**

```
选定智能体预设      → preset 正文
否则 KB 领域已知    → 该领域的默认 base
否则                → 内置通用 base
```

系统 SHALL NOT 拼接多个来源；SHALL NOT 把领域 base 与预设内容合并。

**与 ADR-0003 的关系（边界必须写清）**：本 ADR **只取代 ADR-0003 的决策 3**。ADR-0003 的决策 1（六段模型）、决策 2（一条事实一个 owner）、决策 4（跳过 steering / memory / protocol）、决策 5（条件注入按实际注册工具集）**继续有效**，其 `Status` 保持 `Accepted`，正文不作改动。`README.md` 的"旧 ADR 改 `Superseded by NNNN`"规则针对**整份取代**；半条子决策的取代以本 ADR 正文明示为凭。

## 理由

**最关键的一行：替换之所以安全，不是因为"替换"这个动作对，而是因为"替换 + base 瘦身"是成对的** —— `base` 只装"人设 + 领域方法 + 该模式默认检索方法"，被替换掉的部分不再包含任何系统规则（检索阶梯、联网兜底、完成条件都已移入运行时段）。

- **为什么不叠加**：领域 base 与预设可能就同一件事各说一遍（如"关注报告期口径"），叠加会把两份都留着，违反"一条事实只有一个 owner"（ADR-0003 决策 2）。
- **为什么替换的代价可接受**：选定预设后知识库领域方法不参与组装（"选了财务专家 + 绑定人事库"时人事领域方法消失）。这是既定代价，**不是缺陷** —— 后人不应把它当 bug 去修。
- **⚠ 与调研文档的推荐方向相反，必须记明**：`docs/tmp/deep-research-prompt-management.md` 的原则 3 是"叠加是默认，替换是显式且危险"，其 4.5-2 给用户的推荐默认是"只做默认叠加"。本决策**反其道而行**，支撑理由只有"base 已瘦身"加 WeKnora 的生产先例。**这是本 ADR 最容易被后人回滚的一点**，故列入复查触发条件。
- **预设与领域 base 的定位**：二者是**同一段位（`base`）的互斥候选**，任一时刻只有其一生效 —— 因此两者内容重叠**不构成**"同一事实两个 owner"。定位差异（预设 = 用户显式选择；领域 base = 未选预设时的默认）须登记在 `docs/agents/prompt-ownership.md`，使内容演进时不静默漂移。
- **Anchoring（已核正）**：WeKnora 的自定义正文**只替换 `base`**，运行时各段强制保留 —— 实现在 `internal/agent/prompts.go:400-426` 的 `BuildSystemPromptSections`（模板选择与段拼装），场景表见 `docs/agent-prompt-assembly.md` 的「用户自定义 Agent 正文」行。

## 后果

**正面**：

- `docs/adr/` 恢复"只追加"的一致性（与 ADR-0008 先例一致）。
- "三选一（替换）"成为可独立引用的决策，不再依赖 ADR-0003 正文里的一段修订说明。
- 两处事实引用错误与一处归属错误有处可查。

**负面 / 接受的代价**：

- 与 ADR-0003 形成"半条取代"关系，读者需同时读两份才能拼出完整决策集（边界已在本 ADR 正文明示）。
- 选定预设后领域方法消失的代价不变（见「理由」）。
- 与调研文档的推荐默认相反，存在被后人"改回叠加"的风险。

**不解决的问题**：

- 不解决"一库多域"（领域粒度问题）。
- 不解决"预设与领域方法都要保留"的需求（若出现，按复查条件引入显式开关，见 ADR-0003 决策 4）。
- 不改 ADR-0003 的任何正文与 `Status`。

## 复查触发条件

- **出现"预设与领域方法都要保留"的实际需求** → 引入显式追加开关；⚠ 引入时必须同时规定两者说同一件事时的裁决规则，否则重新引入重复 owner（这正是本次改掉叠加的原因）。
- **"一库一域"假设被打破**（混装 KB 成为常态，如财务 + 人事同库）→ 重新评估 base 的领域解析方式。
- **`base` 再次膨胀**（重新装入跨调用的工具使用习惯或输出规则）→ 替换语义立即变得不安全，须先瘦身，或改回叠加。
- **调研文档的原则 3（叠加为默认）被上游实践普遍证实** → 重新评估本决策。

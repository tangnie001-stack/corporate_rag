# ADR-0017：上下文治理采用四层阶梯；长期记忆限于 episodic + user-semantic

- **Status**：Accepted（**决策 3 记忆底座已被 ADR-0018 取代**，其余仍有效）
- **Date**：2026-10-08
- **Deciders**：用户（决策：破坏式升级、直接采用最佳实践）；Claude（调研与综合）
- **关系**：L0/L1 的横切实现复用 ADR-0016 的 `create_agent` middleware 机制；长期记忆底座沿用 ADR-0004 的单一 PostgreSQL（`pgvector`）；本 ADR **不取代**任何在先 ADR。
- **修订记录**：2026-10-08 原地修订「决策 5」——Phase A 原含 per-model 窗口注册表与探针，经独立架构评审（判 `Request changes`）后**移入 Phase B**。修订理由：在「预算为固定保守值」的 Phase A 中，窗口数值不影响结果，而原设计存在两处 Blocker（工具钩子对结果产生瞬间恒为「当前轮」致截断失效；「阈值 = 上限 − reserve」与「默认预算显著小于上限」自相矛盾）。该 ADR **尚未落地任何代码**，故按本目录规则允许原地修订并留痕。同日（2026-10-08）运行时模型由 `deepseek-v4-pro-0813` 换为 `qwen3.8-2.4t-a95b`（实测输入上限 983,616）；本 ADR 中的窗口数字保持为**决策时点的测量记录**，仅把「运行时模型」的时态限定为「决策时点」。

## 背景与问题

项目当前只有**一层朴素硬截断**，且口径错误、三层能力全缺（实测见 `docs/context-memory-research.md`）：

- `_truncate_history` 的 `context_window` 默认写死 8000、调用点不传参 → 实际预算 **2400 token**；配置 `MODEL_CONTEXT_WINDOW_TOKENS=32768` 从未参与；而**决策时点**的运行时模型（`deepseek-v4-pro-0813`，于 2026-10-08 被 `qwen3.8-2.4t-a95b` 取代，后者输入上限实测 983,616）实测输入窗口为 **1,000,000 token**（probe：545,544 接受 / 1,000,011 拒绝，报错 `Range of input length should be [1, 1000000]`）——配置与事实**相差约 30 倍**。
- 窗口**一模型一值**：同一 provider 下 `qwen3.8-max` ≥ 909,621、`glm-5.3` ≥ 909,573，与 deepseek 的 1,000,000 不同。
- 无持久摘要、无轮内累积上限（实测同轮输入 61,698 token）、无长期记忆。
- **原「不做长期记忆」的决定**（理由：凭记忆回答引入幻觉、与 RAG 溯源原则冲突）在调研中被证明**可以安全翻转**：主流共识是记忆与 RAG **互补**——记忆答「用户是谁、之前发生过什么」，RAG 答「权威来源现在说什么」。

外部一手来源（Anthropic / OpenAI / LangChain / AWS）与 11 个本地参考项目源码在**同一骨架**上收敛：零 LLM 前置瘦身 → 阈值摘要 → 记忆分层。

## 候选方案

| 方案 | 做法 | 代价 | 收益 |
|---|---|---|---|
| A 维持现状 | 继续硬截断、不做记忆 | 口径错误长期存在；多轮语义漂移；轮内可撑爆 | 零改动 |
| B **四层阶梯 + 记忆限 episodic/user-semantic（本决策）** | L0 写入侧治理 → L1 请求前瘦身 → L2 阈值摘要 → L3 长期记忆 Store | 引入压缩的额外 LLM 调用与工程复杂度；需要新依赖 | 与业best practice一致；保住 RAG 溯源；个性化与会话连续性 |
| C 全面记忆（含 semantic 事实记忆，可替代 RAG 作答） | 记忆承载事实并允许凭记忆回答 | 摧毁溯源与可验证性；记忆中毒直接进入答案 | 更少检索调用 |

## 决策

**选 B。** 具体形态：

1. **四层阶梯**（触发顺序）：L0 写入侧治理（零 LLM，工具结果截断/去重/占位）→ L1 请求前瘦身（`pre_model_hook`/middleware，零 LLM，消息级、tool-pair 安全切点）→ L2 阈值摘要（LLM，持久，结构化 user 消息 + boundary + 就地更新不增长）→ L3 长期记忆 Store。
2. **输入上限按 per-model 解析**：注册表（精确 → 前缀/别名 → provider 元数据 → 保守默认）+ 记录 `window_source`；**不在业务代码写死上限数字**。此处的「窗口」是**输入长度上限**（provider 会拒绝的输入上限，实测 `deepseek-v4-pro-0813` = 1,000,000），**不含输出**；输出预算由保留量单独覆盖。上限是**硬上限而非目标**——默认预算**保持保守**，不因上限巨大而追平。
3. **记忆底座**：短期 = LangGraph `checkpointer`（thread）；长期 = `PostgresStore` + `pgvector`（跨 thread、`namespace` 含 `user_id` 多租户）。**本决策确立依赖 `langgraph-checkpoint-postgres`。**
4. **记忆边界**：长期记忆**只承载 episodic + user-semantic**（用户是谁 / 偏好 / 规则 / 经历）；**事实与知识类问题仍强制走 RAG 取证**，记忆不替代证据检索。写入走 background 异步 + 类型化提取 + 重要度门控；遗忘用 TTL / 衰减。
5. **分层落地**：作为四个独立 change 分批实施（A 地基 → B 摘要与 checkpointer → C 长期记忆 → D 外置/缓存/离线整合），**不合并为单个大 change**。其中 Phase A 经独立评审收窄为「历史预算口径收口 + 分词器计数 + 轮内度量」，**不落地 per-model 窗口注册表与探针**——它们随 Phase B（摘要阈值需要窗口数值时）引入。

## 理由

一句话：**「凭记忆答事实」会摧毁溯源，但「记忆只记关于用户的事、事实仍走 RAG」两者可以共存**——这是把原「不做记忆」翻转为「做、但严格限定范围」的关键；其余三条（四层阶梯 / per-model 窗口 / 存储底座）是为这一边界服务的工程形态，且被外部一手来源与 11 个参考项目源码收敛验证。

## 后果

**正面**：

- 上下文有正确的度量（真实窗口 + 分词器计数）与分级治理，取代口径错误的硬截断。
- 在保留 RAG 溯源的前提下获得跨会话个性化与会话连续性。
- 换模型只改注册表；记忆与检索的边界显式化，可被 prompt 规则与测试守住。

**负面 / 接受的代价**：

- **L2 摘要引入额外 LLM 调用**（成本 + 延迟）；摘要**有损**（稳定丢失精确数值/硬约束/决策理由/跨轮依赖/隐性偏好），需靠结构化模板与「不增长」约束缓解，无法根除。
- **记忆是新的攻击面**（记忆中毒；含 compaction-driven write 通道），需来源校验与重要度门控。
- 引入新依赖 `langgraph-checkpoint-postgres`，并带来 Redis / MySQL / checkpointer 三方职责重划的改造量。

**不解决的问题**（明确列出，避免后人误以为本条管了它）：

- 本 ADR 只定**方向**，**不实施**任何一层；L0 的落地见 change `context-window-and-budget-foundation`，L1–L3 各自另开 change。
- **「触顶 → 空回答」缺陷不在本条范围**：既有 `AgentTurnBudget` 的 `jump_to="end"` 路径（ADR-0016 已登记的缺陷路径）在工具未执行时可能产出空 answer；归 `agent-round-budget`（需求池 F-37），本 ADR 不处理。
- **摘要挂载点能否与现用 `build_prompt` 手工分层共存**未验证（Phase B 前置）。
- **记忆的产品语义**（哪些问题允许凭记忆答）未定义，需产品层显式裁定。
- L2/L3 的具体参数（阈值、保留量、摘要模型）不在本条范围。

## 复查触发条件

- 运行时模型的窗口/分词器发生实质变化，或注册表长期依赖 `default` 兜底。
- 压缩带来的额外 LLM 成本或延迟超出预算。
- 出现记忆中毒或「凭记忆答事实」导致溯源失效的实例。
- LangGraph 的 checkpointer / Store API 语义变化（含 `langgraph-checkpoint-postgres` 废弃或破坏性升级）。
- 产品层对「记忆可作答范围」的裁定与本条边界冲突。

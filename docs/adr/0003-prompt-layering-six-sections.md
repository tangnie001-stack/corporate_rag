# ADR-0003：prompt 采用六段模型，运行时各段恒定、base 按三选一（替换）解析

- **Status**：Accepted
- **Date**：2026-09-18
- **Deciders**：用户（决策）；Claude（调研与实测）
- **修订记录（2026-09-18，同日）**：原决策 3 为"`base` = 领域默认 base **+** 预设 overlay（叠加）"，现改为"**三选一（替换）**"。修订发生在**实施之前**（本 ADR 尚未落地任何代码）。

  **为什么不新开一条 ADR 取代**：`README.md` 的"不可变"规则服务于"保留某个时点的决策历史"。但本 ADR 是**一整条决策**，其中六段模型（决策 1/2/4/5）并未改变；为半条子决策新开一条取代 ADR，会把仍然有效的主决策一并作废，反而更难读。故原地修订并在此留痕（含原决策内容）。若本 ADR 已落地代码，则应改为新开一条。

## 背景与问题

### 现状：没有归属规则

`src/config/prompts.py:41` 的注释自述基础段含"一律先检索（不预判范围）、含核心实体才算相关、二次检索加大候选、确认知识库无法覆盖才联网兜底、防滥用 guard" —— 即把**角色 + 处理流程 + 跨调用的工具使用习惯 + 输出规则**混在同一层。仓库里没有任何文档规定"哪一类规则住哪一层"。

### 实证缺陷 1：检索协议住错层，被 persona 整体替换

- `src/rag/prompt.py:48-53`：`if persona: base = persona` —— **整体替换**内置基础段。
- `trace_c54ce259`（2026-09-16）：`[llm] prompt assembled persona_source=preset`，最终 prompt 里只有 `agents/finance-expert.md` 的 4 条工作原则 + 一句"必须先检索"，**检索阶梯（规则 4–8，含唯一出口）完全不在其中**。
- 模型唯一收到的停止条件挂在 `USER_PROMPT_TEMPLATE:98` 的"若**工具仍无法获得**相关信息"上，而 `retrieve_kb` 恒返回非空、从不报失败 → 该条件永不成立。直接后果是 5 轮全在调工具、`answer_len=0`。

### 实证缺陷 2：补丁是部分拷贝，丢失出口

`KB_BOUND_RETRIEVAL_DISCIPLINE`（`prompts.py:74-77`）与基础段规则 2（`:47`）的"不要预先猜测问题是否在知识库范围内"**逐字相同**，但规则 2 尾部的"**全部明显不相关则按第 4 条处理**"（指向阶梯入口）在拷贝版里被删掉。同一条事实两个 owner，且拷贝版漂移。

### 反证：根因是"住错层"，不是"替换动作"

`FORK_EXECUTION_CONTRACT`（`prompts.py:318-322`）从一开始就放在"子代理段"并以无条件追加的方式注入，`prompt.py:279-295` 的实现同样是"追加"。**fork 那条路从未出现过此类问题。** 结论：同一条事实若住在会被覆盖的层，任何替换语义都会丢掉它。

### 缺失的两条运行时规则

| 缺什么 | 后果（已有实测） |
|---|---|
| 停止检索的条件（"证据充分即停止"） | 模型换词盲试到迭代上限 |
| 停止调用工具的条件（"完成时给完整答案"） | `answer_len=0`（5 轮全在 tool_call） |

### 外部结论与同域参照

- **外部明确结论**：没有任何官方机制支持"persona 整体替换 system prompt"。Claude Agent SDK 的 `SystemPromptPreset{type:"preset", append}` 与 `SystemPromptCustom{type:"custom"}` 是两条路，用 `custom` 时官方**不替你保留 base**。
- **WeKnora 九段模型**（生产验证）：`base` / `steering` / `runtime_contract` / `sources` / `tools` / `skills` / `output` / `memory` / `protocol`，唯一入口 `BuildSystemPromptSections`，空段丢弃，每段打 `section=... bytes=...`。关键性质：**base 极薄**（rag 模式仅 5 行，不含检索阶梯/联网规则/停止条件）；**自定义正文只替换 base**，运行时各段恒定；条件注入按**实际 registry** 判断；其文档明写"不要把同一条规则复制到多个模板中来'加强优先级'"。

### 架构定位（触发本决策的前提）

本项目是**通用问答助手**（现阶段偏财务），目标形态是"选定知识库 → 加载该领域 prompt；未选 → 通用回答"，后续可扩展人事等领域。这要求 base **可被领域内容替换**，而运行时契约**恒定不被覆盖**。

## 候选方案

| 方案 | 做法 | 代价 | 收益 |
|---|---|---|---|
| A | 维持两层（base + 环境约束），只把检索阶梯改成无条件注入段 | 归属问题不解决；下一批规则仍会重复 | 最小改动 |
| B | 九段全抄 | `steering` 无代码基础、`memory` 已被消息层承担、`protocol` 依赖已决定不抄的 handle 机制 → 空段或重复 owner | 与参照完全一致 |
| C | **六段**：`base` / `runtime_contract` / `sources` / `tools` / `skills` / `output` | 需要重采快照基线；两条现有测试必然失败 | 命中三个实证缺陷 + 补齐两条缺失规则 |
| D | 完整 section registry + 命名 order 表（deepseek-harness 路线） | 重构面大，且 P1+P2 已能覆盖现有问题 | 长期扩展性最好 |

## 决策

**选 C，并同时确定 base 的解析方式与三个跳过的段：**

1. **六段模型**：`base`（角色/领域方法）/ `runtime_contract`（数据·指令边界 + 完成条件）/ `sources`（来源选择）/ `tools`（通用工具约定）/ `skills`（按需加载的方法论）/ `output`（输出形态 + 引用编码）。组装有唯一入口，空段丢弃。
2. **一条事实一个 owner**：跨调用的工具使用习惯（含检索阶梯）归 `sources`；单工具语义归工具 `description`；输出形态归 `output`；完成条件归 `runtime_contract`。SHALL NOT 把同一条规则复制到多个段来"加强优先级"。
3. **`base` 按三选一（替换）解析**：`选定预设 → preset 正文`；`否则 KB 领域已知 → 该领域默认 base`；`否则 → 内置通用 base`。SHALL NOT 拼接多个来源。（原决策为"领域默认 base + 预设 overlay 叠加"，见头部修订记录。）
4. **跳过三段**：`steering`（插话能力不存在）、`memory`（已由 `_truncate_history` 承担）、`protocol`（handle 机制已决定不采用，引用编码归 `output`）。
5. **条件注入按实际注册的工具集合**，不读配置开关；verify 运行期注入的指引同样受工具集约束。

## 理由

**最关键的一行：根因不是"persona 替换 base"这个动作，而是"检索协议被放在了会被覆盖的层"。** 修法因此是**重分类**，不是"给 persona 加保留"。

- **为什么不选 A**：它只修了检索阶梯这一条。归属问题不解决，下一批规则（例如本次要补的"停止检索""停止调用工具"）仍会散落在 base 里，再被覆盖一次。A 是把同一个缺陷推迟。
- **为什么不选 B**：九段里有三段在本项目没有对应物或已有归属 —— 抄进来只会得到空段（steering、protocol）或重复 owner（memory）。参照项目段数的价值在于"每段有唯一职责",而不是段数本身。
- **为什么不选 D**：P1（归属）+ P2（内容）已能覆盖三个实证缺陷；在段数只有 6、且没有插件化贡献者之前，registry + order band 是为不存在的需求付复杂度（违反项目「最小改动」）。
- **为什么 base 是替换而非叠加**：叠加会把**重复 owner 固化进 prompt** —— 领域 base 与预设可能就同一件事各说一遍（如"关注报告期口径"），两份都留着违反决策 2。而替换之所以安全，是因为**替换与 base 瘦身是成对的**：base 只装"人设 + 领域方法"，被替换掉的部分不再包含任何系统规则。Anchoring：WeKnora 的自定义正文同样**替换** base（`internal/config/agent_prompts.go` 的 `if body != "" { return body }`，文件头注释"never rewrite user content"；`BuildSystemPromptSections` 三选一），其 base 也仅装"角色 + 领域工作流"。
- **为什么必须无条件注入运行时各段**：这是缺陷 1 的直接对照实验结论 —— `FORK_EXECUTION_CONTRACT` 因为住对了层，从未出问题。

## 后果

**正面**：

- 检索阶梯不再被预设覆盖；同时消解缺陷 2 的重复 owner（`KB_BOUND_RETRIEVAL_DISCIPLINE` 常量删除，内容归回唯一 owner 并补回出口）。
- 补齐两条缺失规则（停止检索、停止调用工具），两者都直接命中已实测的失败形态。
- `base` 可被领域内容替换，支撑"选库即切领域"的目标形态；运行时契约恒定。
- 每个段可观测（段字节数日志），prompt 体积变化可见。

**负面 / 接受的代价**：

- **契约变更，两条现有测试必然失败**：`tests/rag/test_prompt_layers.py:24`（persona='' 时首条 system 消息与 `prompt_manager` 输出逐字相同 —— ⚠ 它比的是 `pm.get_system_prompt()`，不是静态快照，且该方法走远端 + 本地兜底）与 `:59`（`assert "基础段正文" not in content`）。**后者保护的正是被移除的缺陷。**改测试不是"为了让测试通过"，是契约本身变了 —— 必须在提交信息里说明。任何以 `pm.get_system_prompt()` 为准的闸门测试都必须显式 pin 到本地兜底，否则不可重复。
- **`src/rag/prompt.py:54-57` 的注释理由已被证伪**（其前提"persona 非空时由预设自己承载等价指引"与 trace 实测相反），需重写为描述当前机制。
- **六段无条件注入净增 system 段体积**：`_truncate_history` 的 token 预算只作用于历史，不含 system → 这是净增。
- **选定预设后知识库领域方法消失（替换语义的既定代价）**：「选了财务专家 + 绑定人事库」时，人事领域方法不参与组装。系统记日志但不阻断。**这是决策 3 的直接代价，不是缺陷** —— 后人不应把它当 bug 去修；若"两者都要"成为实际需求，按"复查触发条件"引入显式开关。
- **需要 `knowledge_base.domain` 列**（一个 migration）；存量 KB 落入通用领域。
- **条件注入需要把启用工具集合传到 verify 注入点**（`src/agents/graph/verify/regen_decision.py`），否则"下掉 `search_web` 但指引仍在"只修了一半。
- **端到端快照需人工重采** —— 本变更唯一不可自动化的验收点。
- 需要新增归属表文档，并登记进 `CLAUDE.md` 文档组织表。

**不解决的问题**（避免后人误以为本 ADR 管了它）：

- 不解决检索取数口径（候选池、去重单位）—— 见 change `retrieval-fetch-and-dedup` 与 ADR-0001。
- 不解决用户中途插话（`steering` 段）。
- 不解决机器可解析的引用句柄（`protocol` 段）。
- 不解决"模型回答前能否看到知识库边界"（库边界可见性属独立项，落在 user message 的运行时上下文，不在本段模型内）。
- **会改变"未绑定知识库"会话（态 A）的 system 段** —— 因为 `runtime_contract`（含完成条件）与 `output` 是无条件注入的。这与库边界项 §3.1 的 G4（"态 A 的 system 段逐字不变"）冲突，**已决定取"结构不变"**：态 A 仍是两条 system 消息、角色序列不变，内容是新的。理由：G4 的原始意图是"别把纯对话搞坏"，而"结构不变"已守住该意图；若改为"仅绑定时注入"，会让"模型 5 轮全在调工具、`answer_len=0`"这类失败形态在纯对话下依然无解（缺的正是完成条件）。
- 不改变 prompt 载体本身（见 ADR-0002）。

## 复查触发条件

- **出现"用户需要在回答执行中途补充指令"的实际需求** → 引入 `steering` 段（WeKnora 的 `<steering_guidance>` 可直接参照）。
- **出现"引用需要机器可解析句柄"的实际需求** → 评估 `protocol` 段（前提是重新评估 handle 机制的取舍）。
- **"一库一域"假设被打破**（混装 KB 成为常态，如财务+人事同库）→ 重新评估 base 的领域解析方式。
- **出现"预设与领域方法都要保留"的实际需求** → 按决策 4 引入显式开关；⚠ 引入时须同时规定两者说同一件事时的裁决规则，否则会重新引入重复 owner（这正是本次改掉叠加的原因）。
- **段数增长或出现段间规则重复** → 说明归属表已不足以约束，此时才引入命名 order 表（方案 D 路线）。
- **六段注入后的 token 净增量不可接受** → 复查哪些段可转为条件注入（但 `runtime_contract` 的完成条件不应转为条件注入，它是无条件性质的）。
